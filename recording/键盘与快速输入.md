# 键盘与快速输入 · 实测研究

> 起因：2026-10-22 录 R05 时，逐字键入 `E:\esp\v6.1` 打出来是 `E:\espk6.1` —— `\` 和 `v` 没了。
> 光靠"再试一次"说不清是输入法、是键位映射、还是 API 的问题，于是搭了一台能**精确回读**的实验台。
> 实验台：`_speedtest/kbd_lab.py`（页面把输入框内容写进窗口标题，外部轮询标题判定，不截图不 OCR）

## 一 结论先行

| 结论 | 数字 |
|---|---|
| **原生应用打字，一律走 SendInput 的 Unicode 通道** | 5/5 全对，12 字 **20–32ms** |
| **老的 `VkKeyScanW + keybd_event` 路线不可用** | **3/5**，中文**静默丢弃**、`-p ` 被输入法吃成 `-拍` |
| **长文本用整段粘贴** | 5/5，**120ms 固定**（不随长度变） |
| **要"打字感"用逐字 Unicode** | 35ms/字 ≈ **28 字/秒**，仍 5/5 |
| **鼠标点击在本机是准的** | **5/5** 命中，2–21ms，坐标零偏差 |

## 二 五种方法 × 五种字符串（单次实测）

字符串：`path` = `E:\esp\v6.1` · `cmd` = `idf.py -p COM3` · `sym` = `100% & ~ #1` · `model` = `WT9932P4-TINY` · `cn` = `你好世界`

| 方法 | path | cmd | sym | model | cn | 正确率 |
|---|---|---:|---:|---:|---:|---:|
| `kb`（VkKeyScanW + keybd_event） | 866 OK | **1083 ✗** | 858 OK | 1039 OK | **0 ✗ 空** | **3/5** |
| `uni`（SendInput Unicode，一次投递） | **20** OK | **32** OK | **26** OK | **28** OK | **7** OK | **5/5** |
| `unigap`（同上，35ms/字） | 430 OK | 550 OK | 420 OK | 502 OK | 153 OK | 5/5 |
| `clip`（整段粘贴） | 129 OK | 121 OK | 122 OK | 119 OK | 125 OK | 5/5 |
| `clipchar`（逐字粘贴） | 1400 OK | 1781 OK | 1423 OK | 1643 OK | 509 OK | 5/5 |

单位 ms（只计投递动作本身，不含中途等待）。

### 三处失败长什么样

1. **`kb` + `cmd`**：`idf.py -p COM3` → **`idf.py-拍COM3`**
   输入法在中文态把 ` -p ` 组合成了「拍」，连空格都被吃掉。**这条最能说明"换机器就复现不了"** —— 取决于当时输入法状态。
2. **`kb` + `cn`**：`你好世界` → **空**，耗时 0ms。
   `VkKeyScanW` 对非 ASCII 返回 -1，`type_text` 里一句 `continue` 就跳过了 —— **不报错、不提示、静默丢**。
3. **`kb` + `path`**：本次 866ms **打对了**。
   所以 R05 那次失败不是必然，是"输入法/焦点状态"叠加出来的偶发 —— 这正是它危险的地方：**没有稳定复现，就没有稳定交付**。

### 速度口径

| 方法 | 单字耗时 | 等效速度 |
|---|---:|---:|
| `uni` | ~1.7ms | **≈600 字/秒** |
| `kb` | ~70ms | ≈14 字/秒 |
| `unigap` | 35ms | ≈28 字/秒 |
| `clipchar` | ~110ms | ≈9 字/秒 |
| `clip` | 固定 ~120ms | 与长度无关 |

## 三 鼠标：本机 5/5，误差来自客户区原点

同一台机器点 5 个 60×60 方块（页面坐标 70/190/310/430/550，y=330）：

```
click t1 @(78,361)  → t1 @70,330   OK   21ms
click t2 @(198,361) → t2 @190,330  OK    6ms
click t3 @(318,361) → t3 @310,330  OK    2ms
click t4 @(438,361) → t4 @430,330  OK    5ms
click t5 @(558,361) → t5 @550,330  OK   10ms
```

**命中点的 client 坐标与页面目标完全一致，误差 0。**

唯一的坑在换算：校准点击 `(300,120)` 时，页面收到的 client 是 `(292,89)` ——
**窗口有 8px 左边框、31px 标题栏**。不校准直接按窗口坐标点，就会稳定偏 (8,31)。

> 结论：**鼠标不是不准，是"窗口坐标 ≠ 客户区坐标"没换算。** 点之前先点一个已知目标校准。

| 来源 | 说了什么 | 与本机实测的关系 |
|---|---|---|

## 六 七条规矩

1. **原生应用打字只用 `type_unicode`**。别碰 `VkKeyScanW` —— 它依赖键盘布局，还把中文静默丢掉。
2. **中文没有第二条路**：Unicode 通道，或剪贴板。`keybd_event` 打不出来，且不报错。
3. **长文本用 `paste_text`**：120ms 固定，不随长度涨；记得 `restore=True`。
4. **要打字感用 `typehuman`**：55ms/字 ≈ 18 字/秒，接近真人；35ms 偏快但更省时间。
5. **点之前先校准客户区原点**：窗口边框和标题栏都要算进去，别假设窗口在 (0,0) 就等于页面在 (0,0)。
6. **断言要轮询，别 sleep 定值**：窗口标题回读实测有 **100–250ms** 延迟；固定等 200ms 会读到上一次的结果。
7. **空字段不产生事件**：想证明"清空了"，得先打一个哨兵字符逼出一次更新，否则永远读不到新状态。

## 七 没测的（别当成已验证）

| 项 | 为什么没测 |
|---|---|
| **CDP `Input.insertText`** | 网页侧理论上最快（连系统输入都不走），但要走 puppeteer 连接，本轮没搭 |
| **UIPI：管理员窗口** | 需要提权起一个管理员窗口，风险和打扰都大 |
| **5000 字符上限** | 只按文档分片规避，没做边界实测 |
| **多键盘布局**（法语 AZERTY 等） | 本机只有一种布局；`kb` 那条的布局依赖是**推断**，不是实测 |
| **远程桌面 / RDP 会话** | 未测，SendInput 在 RDP 下行为可能不同 |
