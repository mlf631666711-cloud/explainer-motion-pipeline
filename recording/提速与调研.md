# 提速与调研（2026-10-22）

> 触发：需求方「提高你的阅读速度和录屏速度 联网调研看看有没有新的操作思路」。
> 本文只写**已经落地或已实测否决**的东西，不写"据说可以"。

---

## 0 一句话结论

| 原来的做法 | 新做法 | 收益 |
|---|---|---|
| 截屏 + 放大 + 肉眼数像素，猜坐标 | **CDP 读 `getBoundingClientRect`** | 0 误差，省掉 3–5 轮"截图→看图→改坐标" |
| 开录前设一次剪贴板，祈祷别被抢 | **录制脚本内置 `clip` 动作，粘贴前 0.05s 再写一次** | 剪贴板类废片从"每次"降到"0" |
| 每次录前调 `focus(size,pos)` | **`win_pos.py`：先读 rect，已达标就跳过** | 避开 `SetWindowPos` 卡死 3 分钟（RC-007） |
| 抽 8 帧存 8 张图，一张张看 | **先差分定位事件，再裁 ROI 拼一张网格** | 看图轮次从 8 降到 1–2 |

## 1 思路一：用 CDP 读 DOM，代替截图像素（已落地）

### 为什么

Electron 应用（VS Code、Slack、Discord、Obsidian…）本质是 Chromium。
启动时加 `--remote-debugging-port=9222`，就能用 puppeteer/playwright 连上去读 DOM：

```bash
# 启动（必须清掉 ELECTRON_RUN_AS_NODE，否则被当纯 Node 跑，见 RC-001）
code --remote-debugging-port=9222 --new-window

# 读元素矩形（本项目工具）
node 工具/cdp_dump.cjs '[".activitybar .action-item",".monaco-list-row"]'
```

### 拿到什么

```json
{"vp":[1904,1072], "q":{".monaco-list-row":[
  {"t":"ESP-IDF, 2.3.0, 已验证的发布者 Espressif Systems","b":[53,641,289,72]}
]}}
```

`b` = `[x, y, w, h]`，直接就是标注要的那组数。

### ★ 三个必踩的坑

1. **多窗口**：`pages()` 会返回所有窗口的 renderer。本项目实测读到过一个
   **已经最小化、3440 宽的旧窗口**，报 `innerWidth=3440`，而实际在录的窗口是 1920。
   ⇒ 必须按 `innerWidth` 挑出目标窗口（`cdp_probe.cjs` 的第二个参数就是干这个的）。
2. **水平偏移 +8**：CSS `x` 加 8 才是屏幕像素（窗口左框）。
   `y` 完全一致。实测校验：搜索框 CDP `x=57` / 屏幕实测 `x=65`，`y=72` 两边相同。
3. **CDP 说 UI 元素在哪，不等于"那一刻画面上它在哪"**：UI 会滚动、列表会换内容。
   坐标仍必须在**素材帧**上复核（见 §4）。

### 边界

- 只对 Electron / Chromium 系有效。原生 Win32（EIM 安装器那种 Flutter/RN 窗口）读不到，仍得走像素。
- 需要改启动参数。已经在跑的实例不认这个 flag。

## 2 思路二：剪贴板动作内置到录制脚本（已落地）

### 现象

R09 第一次录制，搜索框里粘出来的是「**某个电商商品名**」——
需求方剪贴板里某个电商商品名。本机有常驻程序会**随时改写剪贴板**（RC-002）。

"开录前设一次"救不了：从设完到 Ctrl+V 之间隔着 10 秒，够被改三次。

### 做法

给 `auto_record.py` 加动作 `{"do":"clip","text":"esp-idf"}`，
用 Win32 `OpenClipboard / EmptyClipboard / SetClipboardData` 直接写（不走 PowerShell、不起进程）。

脚本里这样排：

```json
{"do":"press","vk":46},              // Del 清空
{"do":"wait","s":0.40},
{"do":"clip","text":"esp-idf"},      // ★ 粘贴前 0.05s 才写
{"do":"wait","s":0.05},
{"do":"hotkey","mod":17,"vk":86}     // Ctrl+V
```

### ★ 64 位必须声明 restype

```python
k32.GlobalAlloc.restype = wintypes.HGLOBAL   # 不写就按 c_int 收，句柄被截成 0
k32.GlobalLock.restype  = wintypes.LPVOID    # ⇒ memmove 写地址 0 ⇒ access violation
```

这条不写就是 `OSError: access violation writing 0x0000000000000000`，很难一眼看出是句柄截断。

## 3 思路三：ddagrab（调研了，**暂不换**）

FFmpeg 官方 wiki 与 ffmpeg-cookbook 都指向 **Desktop Duplication API（ddagrab 滤镜）**：
拿 D3D11 纹理，CPU 占用接近 0，能上 60/120fps，几乎不撕裂；`gdigrab` 走 GDI，30fps 以上就掉帧。

```bash
# 官方式样
ffmpeg -init_hw_device d3d11va -filter_complex ddagrab=0 -c:v h264_nvenc -cq:v 20 out.mkv
# 或下载回内存再用 libx264
ffmpeg -filter_complex ddagrab=0,hwdownload,format=bgra -c:v libx264 -crf 20 out.mkv
```

**为什么本轮不换**：

- 本项目录的是 **1920×1080 / 30fps / 15–20 秒**，gdigrab 完全跟得上，没掉过帧；
- `ddagrab` 只抓整屏，**不能按窗口抓**（论坛确认 Windows.Graphics.Capture 至今未进 FFmpeg），
  而本项目的做法恰恰是"把窗口钉成 1920×1080 再抓这块区域"；
- 换它要加 `hwdownload`，多一层格式转换，色彩链要重新验（见总规格锁 §24）。

**什么时候该换**：录 4K 以上、或 60fps 素材、或多显示器拼接。届时再用它。

## 4 阅读提速：从"看图"改成"算像素"

原来读素材的流程是：抽 8 帧 → 存 8 张 → Read 8 次 → 肉眼比对。
现在固定成三步，**几乎不看图**：

### ① 先差分，定位事件时刻

```bash
ffmpeg -i in.mp4 -vf "scale=240:135,format=gray" -f rawvideo -pix_fmt gray out.raw
# python：逐帧 |Δ| 求均值，取局部极大
```

一次就能拿到"面板何时展开 / 结果何时出现 / 列表何时切换"。

### ② 再按 ROI 精测（整体差分看不见小变化，比如搜索框里多了一行字）

```bash
ffmpeg -i in.mp4 -vf "crop=281:26:57:72,scale=141:13,format=gray" -f rawvideo -pix_fmt gray roi.raw
```

搜索词出现这种"只有几十个像素变了"的事件，必须把 ROI 缩到那个框上才测得出来。

### ③ 最后才看图，而且一次看多帧

裁同一个 ROI、缩到 440 宽、`hstack/vstack` 拼一张。
**一张图看 6 个时刻**，而不是 6 张图看 1 个时刻。

### ★ 本轮靠这套抓到的一个真错误

我原先按 ROI 峰值把 `7.00s` 判成"搜索结果出现"，
实际上那是 **Ctrl+A+Del 把列表清空**；结果真正出现是 `8.43s`。

如果靠看 8 张图猜，很可能就把红框卡在空列表上——**而那正是需求方说的"标注是歪的"**。

## 4.5 ★ gdigrab 帧率实测（2026-10-22 晚 · 第一次有数）

之前一直**假设**"1080p/30fps 不掉帧"，从没测过。这次补上。
方法：`_speedtest/run_fps_test.sh` 各档录 10 秒，`ffprobe -count_frames` 数实际帧；
再用 `_speedtest/gap.py` 读每帧 PTS 间隔，区分"丢帧"和"时间戳抖动"。

| 档 | 期望 | 实测 | 保真率 | 间隔分布 | 判断 |
|---|---:|---:|---:|---|---|
| **1920×1080@30** | 300 | **300** | **100%** | 33ms×273 / 67ms×**26** | 帧数达标，**但有 8.7% 的间隔翻倍** |
| 1920×1080@60 | 600 | 553 | 92.2% | 17ms×440 / 33ms×112 | 抖动 20% |
| 2560×1080@30 | 300 | 300 | 100% | 33ms×~275 | 与 1080p 同级 |
| 3440×1440@30 | 300 | 275 | 91.7% | 33ms×249 / 67ms×25 | 掉 8.3% |
| 3440×1440@60 | 600 | 282 | **47.0%** | **33ms×251** / 50ms×24 | **不是丢帧，是降到 30fps 在抓** |

### 三条结论

1. **`--region 1920×1080@30` 就是这套工具的甜点** —— 帧数 100% 达标。
   这不只是省资源，是**唯一能让帧数完全对上的档位**。
2. **60fps 不可用**：1080p 掉 8%，3440×1440 直接**降速成 30fps**
   （中位间隔 33ms 而不是 17ms）—— 那种"帧数只有一半"不是丢帧，是 gdigrab 干脆抓不过来。
3. **忘了给 `--region` 会真掉帧**：全屏 3440×1440@30 只有 91.7%。
   铁律 1「必须给 --region」第一次有了量化依据，不再只是"产物会废"。

### ★ 一个之前不知道的事：1080p@30 也有时间戳抖动

帧数明明够 300，但间隔里有 **26 次 67ms**（等于丢一帧再补回来）。
`≥2.5×` 的大间隔 0 次 ⇒ **没有"卡死一下"**，是**细碎抖动**。
成片观感上是轻微不匀，不是明显卡顿 —— 这也是项目一直没察觉的原因。

要更稳只有两条路：降到 720p（未测，预期更稳），或换 ddagrab（见 §3，会丢掉"按窗口抓"的能力）。

## 4.6 ★ 编码器实测：这一环已经到顶，没有提速空间（2026-10-22 晚）

### 先排除一个：NVENC 用不了

`h264_nvenc` 在编码器列表里，但一跑就报：

```
Driver does not support the required nvenc API version. Required: 13.1 Found: 13.0
The minimum required Nvidia driver for nvenc is 610.00 or newer
```

本机 RTX 4060 的驱动只到 13.0。**升级驱动前，硬件编码这条路走不通**，
所有提速只能靠 x264 的参数。

### x264 预设：真素材上重编码

源 = `rec_1920x1080_30.mp4`（300 帧真实桌面内容），crf 23：

| 预设 | 编码耗时 | 体积 | 相对 ultrafast |
|---|---:|---:|---:|
| ultrafast | 0.64s | 0.48MB | 1.00× |
| superfast | 0.79s | 0.26MB | 1.24× |
| **veryfast** | **0.84s** | **0.16MB** | **1.32×** |
| faster | 0.97s | 0.17MB | 1.52× |
| medium | 0.98s | 0.20MB | 1.53× |

**0.64 秒编完 10 秒素材 = 15.6× 实时**。也就是说：**实时录制时，编码根本不是瓶颈**，
拿这点耗时去换 3 倍体积，划得来。

### ★ 实时录制下验证：三档全部 100%

| 预设 | 帧数 | 保真 | 体积 |
|---|---:|---:|---:|
| ultrafast | 300/300 | 100% | 0.91 MB |
| **veryfast** | **300/300** | **100%** | **0.31 MB** |
| medium | 300/300 | 100% | 0.39 MB |

**结论：换 veryfast，帧数一帧不掉，体积降到 1/3。**

### 为什么 medium 反而不如 veryfast

静态桌面素材上，`medium` 的码率分配策略不占优，且它没有 fast 系预设那种激进的 skip 优化。
**"更慢的预设 = 更小体积"在录屏这种内容上不成立** —— 别按直觉选。

### 直接可用的参数

```bash
-c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p
```

- **crf 对速度几乎无影响**（18/23/28 都是 1.10s 左右），是**免费的质量旋钮**
- crf 18 体积 1.23MB / 23 是 0.66MB / 28 是 0.41MB ⇒ 需要小文件就调 crf，别调预设

### ★ 结论要收窄：项目参数已经是对的了

我一开始写的是"项目一直用 ultrafast、保守过头"，**这条是错的** ——
查了 `auto_record.py:260`，项目**早就是 `veryfast + crf 18`**，不是 ultrafast。
基线是我自己拿 ultrafast 当的。

补测项目实际参数（veryfast）：

| crf | 耗时 | 体积（10s / 1080p） |
|---|---:|---:|
| **18（项目当前）** | 0.81s | **0.23MB** |
| 20 | 0.85s | 0.20MB |
| 23 | 0.82s | 0.16MB |
| 26 | 0.80s | 0.14MB |

**crf 对速度毫无影响**（0.80–0.85s，纯噪声），只影响体积。
想让文件更小，把 crf 调到 20–22 能省 15–30%，质量对录屏仍够；但那是**省空间，不是提速**。

### 真正的结论：编码不是瓶颈，提速要到别处找

- 0.8 秒编完 10 秒素材 = **12× 实时余量**
- 三档预设实时录制**全部 300/300 帧**
- ⇒ **换预设、调 crf，对"录多久"没有任何影响**

**能提速的地方只剩流程本身**：等待时长（`--dur` / `wait`）、窗口启动、
以及别在录制时跑别的重活。编码这一块，已经不用再研究了。

## 4.7 ★ 单条案例端到端计时：R05（2026-10-22 深夜 · n=1）

需求方要一个"跑一条录屏案例到底要多久"的实数。选 R05（安装路径），因为它是清单里第一条还没录出来的。

### 时间线（秒表口径）

| 阶段 | 实测 | 说明 |
|---|---:|---|
| 安装器启动 → 窗口可交互 | **2.93s** | `eim-gui-windows-x64.exe` |
| 钉窗口 `win_pos.py` | **0.71s** | 幂等；已在目标位就秒回 |
| 向导开到第 8 步（人工） | 5m12s | **不计入工具耗时** —— 这是"准备现场"，不是录制 |
| `auto_record.py` 本体（6.0s 素材） | **9.55s** | 关通知 → 预热点击 → 采集 → 收尾 |
| 校验（数帧 + 抽 3 帧） | **0.74s** | ffprobe + ffmpeg |

**工具侧合计 11.0s，产出一条 6.0s / 1080p 素材。**

### 素材实测

- 1920×1080 · 30fps · 6.000s · 94KB
- **172 帧（应 180）**：`163×33ms + 8×67ms`，丢 8 帧 = **4.4%**，无长卡顿
- 画面：`C:\esp` → `E:\esp\v6.1`，下方提示变成「路径 E:\esp\v6.1 有效。」

### 三处现场踩到的坑

1. **UI 内容区不重绘**：`SetWindowPos` 把窗口改成 1920×1080 后，右侧内容区**空白**，但左边步骤号照走；
   **给一次点击/按键才重绘**。录之前必须点一下窗口再看一眼画面，否则录出来是白卡。
2. **点击路径输入框会弹出目录选择框**（一个 "my computer" 小窗），**字段本身不能直接打字**。
   第一次能直接粘贴，是因为向导刚切页、输入框已带焦点，点一下只是聚焦 —— **换个时机就弹框**。
3. **逐字键入会丢字符**：`VkKeyScanW` 走 `keybd_event` 打 `E:\esp\v6.1`，实测得到 `E:\espk6.1`
   —— **`\` 和 `v` 都被吞**。路径类输入**只用剪贴板整段粘贴**，别逐字敲（RC-011 的又一条实证）。

### 结论

- **一条 6s 素材 ≈ 11s 墙钟**：录制本体只占 6s，其余 5s 是开关通知 / 预热 / 收尾 / 校验。
- 真正费时间的是**把应用开到目标页面**（本例 5 分钟，含人工试错），这一步还没自动化。
- 帧数不是 100%：1080p@30 下仍丢 4.4%。和 §4.5 的 300/300 不矛盾 —— 那次是静止桌面，这次安装器一直在重绘。

## 4.8 ★ 20 秒素材要录多久（2026-10-22 深夜 · 两次采样）

问的是"录一条 20 秒的到底花多久"。答案是 **23.5 秒**，和 6 秒那条一起看，能拆出固定开销。

| 素材时长 | 墙钟全程 | 固定开销 | 帧数 | 丢帧 |
|---:|---:|---:|---:|---:|
| 6.0s（R05） | 9.55s | 3.55s | 172 / 180 | 4.4% |
| **20.0s** | **23.46s** | **3.46s** | **568 / 600** | **5.3%** |

**公式：墙钟 ≈ 素材时长 + 3.5s。** 再加校验（数帧 + 抽 3 帧，0.74s），一条 20s 素材
从敲命令到"确认能用"大约 **24.2 秒**。

### 那 3.5 秒花在哪

关通知 → 预热（focus + 吃掉第一次点击）→ ffmpeg 起头 → 录完关通知 → 收尾写 moov。
**和素材长度无关**，所以越长的素材，相对开销越低（6s 素材的白白多出 37%，20s 只有 17%）。

### 帧数：丢的是"连续的 5%"，不是开头一口气

20s 那条：**535×33ms + 32×67ms，没有 ≥100ms 的断点**。
6s 那条：163×33ms + 8×67ms。两条都是"每隔十几帧漏一帧"，**不是启动时丢一批**。

⇒ 结论：**丢帧率约 4–5%，且随时长线性堆积**。20 秒素材实际少 1.07 秒有效帧，
动作快的地方（点击、弹窗）需要留意，必要时重录或用 60fps（但 §4.5 已证明 60fps 抓不住）。

### 这一轮另外撞到两个真问题

1. **`focus()` 报"没找到窗口"，其实是抢不到前台。**
   `SetForegroundWindow` 被"前台锁定"挡掉时**静默失败**（返回值不说明问题），
   原代码用 `GetForegroundWindow()==h` 判定，失败就报成"窗口不存在"，方向全错。
   已加 `AttachThreadInput` 借用前台线程输入队列的兜底，并改了文案。
2. **常驻置顶类软件会硬占前台。** 本轮「剪映专业版」一直占着前台，
   `SetForegroundWindow`、`AttachThreadInput`、`SwitchToThisWindow` **三种都抢不回来**。
   ⇒ **录之前先把这类程序关掉或最小化**，否则自动录制会把别人的画面录进去
   （本轮 20s 样片第 15 秒就录进了剪映，正是"抽帧看"救回来的）。

## 5 新增的坑（已进 BUG 库）

| 编号 | 现象 | 根因 |
|---|---|---|
| RC-013 | CDP 报 `innerWidth=3440`，与实际 1920 窗口不符 | 读到了另一个最小化窗口的 renderer |

| RC-015 | 一屏同时亮起好几个红框 | `anno-kit.tick()` 丢掉 `draw()` 返回值，过 t1 不消失 |

| RC-018 | 红框整体偏 19px，横跨两项 | 把"已安装"列表的 `y=137` 套到"搜索结果"上（那边是 109） |
